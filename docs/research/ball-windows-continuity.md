## 1. M9：視窗結果相同，耗時未過線

候選完全重用 `pick(rows, hand, lag=0, slack=15, who=who, low=False)`，多軌姿態、float64 轉換與寬高比均與正式 CLI 相同。`estimate_lag` 會找聲音前 15 至後 3 格的轉向；轉向還依賴局部最大值 ±6、速度 ±4、短缺值內插最多 4 格的端點。因此每個聲音保留 `ceil(t*60−29)` 至 `floor(t*60+17)`，兩端含括。先合併為遮罩，重疊不重算，片端裁到影片範圍。

實驗版 `main(src, out, device=None, windows=None)` 接受整數半開區間 `(start, stop)`；未傳視窗仍跑整片。沿用整片 25 格背景取樣、4 格歷史、片頭複製及原 16 格批次；整個批次都在窗外才跳過模型，窗外輸出 NaN，輸出長度不變。這避免更換批次形狀混入數值差異；仍解碼整片，沒有把解碼時間排除在量測之外。

## 1.2 #59 收尾：批次重組與必要格縮放

日期：2026-11-17（台灣時間）。本輪以 `f33a6c1ad855f7f94f931826d37090a58e99ec26` 為 main 基準，先做 profile，再選最小改動；M10 與 lag 上限沿用第 2、3 節負結果，不重做或改門檻。

A2 main 視窗版插入階段計時的總牆鐘為 63.11 秒。MPS 張量階段另同步後才計推論，故此 profile 含額外同步，效能驗收另外使用未插計時的 main（61.17 秒）。

這是父程序各階段的牆鐘等待，解碼與 GPU 可以重疊，不是 ffmpeg 的總 CPU 時間。事前預測推論／張量 75–90%、解碼加縮放 8–20%、背景 1–5%、啟動模型 1–5%、存檔 <1%；實際前兩組為 74.21%／22.55%，背景低於預測。據此保留完整 ffmpeg 解碼，只對視窗及其前三格歷史做縮放，並將所選格跨視窗重新組成 16 格批次。背景仍取原本整片 25 格，不改模型輸入；未嘗試 seek 或變更背景，因本次 profile 顯示解碼讀取僅約 3%，先驗證必要縮放與推論減算。

每個選中格都保留自己的四格序列，片頭仍複製第 0 格，跨窗不把另一個窗的末格當歷史；最後不足 16 格才用小批次。輸出仍是全片長度，窗外 NaN，空候選不載入模型。未給視窗保留既有全片批次與運算路徑。

## 2. M10：少量刪點讓 lag 改變，24 fps 召回下降

先寫失敗方式與測試，再實作固定規則：將相鄰格位移化成 frame heights（x乘寬高比），距離≤0.15才連線；一個點至少要有一側相鄰格連線才保留。使用原軌一次決定，不連鎖刪除、不跨 NaN 補線、兩格短軌可保留。孤立點和超距跳點均設整列NaN，原輸入不變，沒有另調距離門檻。

單元測試先因缺少函式失敗，實作後通過：空軌、全NaN、單點、片端、兩格支持、缺格、跳出去再回來、寬高比及含括門檻。因下列真實E2E退步，函式與測試未進正式程式。

## 3. lag合理性：開發片無法選上限，D的修復仍是診斷

事前固定低fps回退候選：上限0／2／3／4／6格及原算法；`abs(lag)`超出上限即回退0，不把lag截斷成上限。只用四支開發片做leave-one-video-out：每折排除整片，以訓練片召回退步總量最少、逐片等權F2最高、改動較少、固定列舉順序（原算法、0、2、3、4、6）決勝。A1／A2是同場次，這不是逐場次留出。

四片原lag全部0，六個候選在每折訓練／留出上的完整事件都相同；依事前平手規則四折均選原算法。**LOVO無法辨識任何上限，更不能宣稱它選出了2格。** 沒有部署一個只靠D已知失敗選出的門檻；仍需要開發片中實際有非零、且具接觸真值的lag案例。

為完成留言的合理性診斷，在碰B–E前另凍結「只比較原算法和事前列出的固定2格回退」；四片各做一次，不比較其他上限、不改姿態或候選門檻、不用結果回選設計。**D是因為#62的診斷才被注意到，原失效結果已知，不能當作完全未觸碰的新驗證。** 這個固定對照不是LOVO選出的正式規則。
