# 非 16:9 proxy 補邊驗證

基準為 main `1f2807b`（分析工具與後續同步的 `fd379c6` 逐位元相同），資料為 THETIS 的正拍、反拍、平擊發球各 8 支，共 24 拍。每類依檔名排序取前 8 支，在執行前固定；不因結果替換樣本。解析度均為 640×480，ffprobe 實測來源為 17–19 fps。

## 比較方式

THETIS 每支是一拍空揮，沒有擊球聲或球，因此不以聲音候選數計算偵測率。先用原片等比例影像推論，取可見右手腕在來源格上的最大像素位移速度，固定該格的時間；原片參照、拉伸版、補邊版共用同一個時間與 60 fps 索引。膝角與高度沿用 `metrics.measure_full` 的既有定義，沒有縮短量測窗。

7 支的參考格早於第 48 格，膝角前置窗不足，所以膝角只有 17 個有效配對；高度有 24 個。這些是空揮時的手腕參考高度，不是真正球拍觸球的實測高度。

「幾何誤差」將同一原片骨架分別做拉伸或補邊，與原片像素等比例座標比較；「推論誤差」另跑三種影像的姿態模型，再與原片推論比較。原片推論是共同參照，不是人工標註真值。

## 預測與實際

|---|---|---|
| 4:3 幾何 | 720×540，左右各 120 px | 符合 |
| 3:4 幾何 | 540×720，上下各 120 px | 符合 |
| 21:9 幾何 | 960×412，上下各 64 px | 符合；尺寸與偏移依 yuv420 對齊偶數 |

| 參考格有姿態的影片比例 | 不低於拉伸版減 2 個百分點 | 拉伸 24/24、補邊 24/24，差 0 個百分點 |

補邊版與拉伸版的膝角差異超過門檻，因為拉伸本身會扭曲角度，正是本次要修正的問題。依協調者裁定，以對原片等比例參照的誤差下降作為修正驗收，原本 <3° 門檻如實保留為未達。同一骨架的高度幾何誤差在既有兩位小數輸出下，兩版中位數皆為 0.00；高度的改善主要見於獨立推論結果。額外列出的 3D 膝角兩版差中位數為 18.94°，對原片參照的誤差由 18.69° 降至 0.69°，同樣不能宣稱兩版差 <3°。非 16:9 舊場次重算後的 3D 膝角會明顯變動，舊數字與新數字不能直接比較。

追球對 24 支補邊與拉伸 proxy 各跑一次全片 `ball.py`，沒有傳聲音候選視窗，確實載入模型；每支補邊結果均斷言所有有限座標都在內容區。補邊版 83 個無球誤偵測點仍是限制，不能說整片完全沒有假球。

## 16:9 相容性

macOS 的 `h264_videotoolbox` 控制實驗：兩次完全相同的 main ffmpeg 命令，MP4 有 2 bytes 不同，差異位於私有 SEI；解碼 RGB 全部相同。依協調者裁定，保留正式命令，以完整參數與全部影格 `framemd5` 比較硬體編碼輸出，另以固定 libx264 合成片驗整份 MP4。

合成橫式／直式 16:9 均通過，兩邊 `framemd5` 檔案的 SHA256：

| 格式 | main | 補邊分支 |
|---|---|---|
| 橫式 | `c36a0efd34d39f4f98fb8effb3ac6f85463484cc1c622ed017dcc48f0de5f232` | `c36a0efd34d39f4f98fb8effb3ac6f85463484cc1c622ed017dcc48f0de5f232` |
| 直式 | `5c2810f3d5c6299b5fd13e4f093a64da3d16c6774196a27b8f1fd828f5703c7f` | `5c2810f3d5c6299b5fd13e4f093a64da3d16c6774196a27b8f1fd828f5703c7f` |
| 對牆影片 A 第 1 段 | `c6b717c40999f6ec993e822a9a3c4fee4a2bc130658a19138ea1ec158a98d283` | `c6b717c40999f6ec993e822a9a3c4fee4a2bc130658a19138ea1ec158a98d283` |
| 對牆影片 A 第 2 段 | `74bdbb9d8254bdcfbf3fa7390109147e5221c22618ea1b43d1a624865ab81268` | `74bdbb9d8254bdcfbf3fa7390109147e5221c22618ea1b43d1a624865ab81268` |
| 對牆影片 A 第 3 段 | `ee325f603d2fd214a77d0ca9a03ca1b7f51ab153a8d9b42e3035c8019de5e018` | `ee325f603d2fd214a77d0ca9a03ca1b7f51ab153a8d9b42e3035c8019de5e018` |

固定 libx264 的橫直合成片整份 MP4 比較相同。使用者的對牆影片 A 三段，所有姿態／世界座標軌與事件共 11 份 NPY，`cmp` 均相同；完整 ffmpeg 參數與全格 framemd5 也相同。N=1 短片的 `pose.npy`／`pose_world.npy` 兩份輸出，以及同支 16:9 來源全片追球的 `ball.npy`，`cmp` 全部相同。

補邊條件集中在 `proxy.needs_padding()`，沿用原 prep 的整數判斷：`100 * abs(w * ph - h * pw) > h * pw` 才補邊。`layout()`、濾鏡與正反映射共用這個判斷，prep 的版本記錄也使用相同條件；pose、sheet 與標註透過共用濾鏡／映射取得一致結果。標註的尺寸探測共用 `prep.probe_rate()`，同時讀取 side data 與旋轉標籤，接受 `-90.0` 等浮點字串，side data 優先。

| 審查修正預測 | 實際驗證 |
|---|---|
| 1920×1088、1088×1920、854×480、1920×1078 沿用 main | 四種濾鏡皆為原 `scale=960:540` 或 `scale=540:960`；正反映射回傳原物件；不寫版本記錄，模擬既有快取時 ffmpeg 與下游 Python 呼叫皆為 0 |
| ±1% 邊界內保留、超過才補邊 | 橫直四個邊界尺寸均保留；四個超界尺寸與 1440×1080、480×640 仍補邊 |
| 原片標註與 prep 旋轉尺寸一致 | 四組旋轉資料測試通過，包括浮點 side data、浮點旋轉標籤、side data 優先與 180° 不交換寬高 |

上述測試先重現近似比例濾鏡與旋轉尺寸不一致的紅燈，再修正為綠燈；4:3 的實作結果與精確 16:9 命令未變，因此沿用前述實片比較證據，另重跑完整合成 prep 與標註 E2E。

## 舊場次重算

METHOD 維持原值。16:9 與比例偏差 ±1% 內的來源延用既有濾鏡與快取，不因本次改版重算，也不寫補邊版本記錄。超出容許範圍的 `proxy_filter.txt` 記錄成功輸出的完整空間濾鏡；缺記錄或濾鏡不同時，重新執行 prep 會先重建 proxy，再依相依時間戳重算姿態、球軌與事件。版本記錄在 ffmpeg 成功之後才寫入，失敗可續跑。中斷後請重跑 `prep`，完成後再執行下游工具。

之後需重跑 candidates 產生原片座標正確的 sheet，依既有流程核對候選與標註，再更新下游產物；既有標註不會自動當作重新核對過。只有 proxy 的 fallback sheet 保持 proxy 座標。原片標註影片也需重新匯出；新補邊場次以相同版本記錄辨識，繪圖前反映射所有軌，骨架、標籤、避讓框與即時 2D 膝角共用原片座標。

## 2D 座標使用處查核

以 `rg` 搜尋姿態載入、影格解碼、匯出、繪圖與量測呼叫，逐一核對使用的畫面與尺寸：

| 使用處 | 狀態與理由 |
|---|---|
| `pose_full.py` 原片裁切／低 fps 全畫面 | 已處理；前者儲存前映射，後者解碼即補邊，統一輸出 proxy 座標 |
| `candidates.py` 原片 sheet／`frames()` | 已處理；解碼原片後反映射所有人的姿態；`frames()` 本身只按時間解碼，沒有姿態運算 |
| `candidates.py` fallback、legacy、身份確認圖 | 不需反映射；影格與姿態都取自 proxy |
| `annotate.py` 原片標註匯出 | 已處理；有版本記錄才反映射所有軌，沿用原片縮放；骨架／標籤／bbox／2D 膝角都取同一組姿態 |
| `export_session.py` 每拍 clip 與姿態 JSON | 不需反映射；影片裁自 proxy，JSON 同時保留 proxy 姿態與 `size` |
| `highlights.py`／reel | 不需反映射；讀上述 clip、`frames` 與 `size`，裁切／骨架／膝角均在相同 proxy 座標 |
| `strip.py` | 不需反映射；讀每拍 proxy clip，以其實際寬高裁切 `frames` |
| `assemble.py`／`metrics.py`／`refine.py`／`kind.py` | 不需反映射；全片由 proxy 取得尺寸、clip 由 JSON 的 `size` 量測；2D 點差消除補邊平移，像素尺度與畫面一致 |
| `prep.py` 慣用手／`events.py`／`match.py`／`attrib.py` | 不需反映射；姿態與球都對應 proxy，使用 proxy 尺寸或其寬高比 |
| `build_site.py`／網頁骨架、比較放大與曲線 | 不需反映射；匯出的 proxy clip 配對相同 `frames`／`size`，畫布也依影片尺寸定位 |
| `eval_attrib.py`／`eval_lr_swap.py` | 不需反映射；前者讀 proxy 尺寸，後者讀已儲存的 proxy `size`，沒有原片繪圖 |
| `eval_knee2d_gate.py`、THETIS 評估系列、研究腳本 | 本次不影響；使用各自既有固定尺寸研究輸入，未改為讀本次 prep 的新輸出；研究裁切圖也以對應 proxy 取格。固定原片尺寸的歷史研究工具不能直接混入新補邊姿態 |

## 可重現檢查

```sh
.venv/bin/python tests/test_proxy.py
.venv/bin/python tests/test_annotate.py
.venv/bin/python tests/test_pose_full.py
.venv/bin/python tests/test_prep_ball.py
.venv/bin/python tests/test_prep_e2e.py
```

單元測試先因缺少補邊模組而紅燈，實作後通過；把原片路徑測試指向 main 的 pose_full，仍會因拉伸濾鏡而失敗。合成 E2E 使用真實 ffmpeg、姿態、追球模型，包含黑邊像素、舊非 16:9 快取重算與第二次執行不重算。

首輪三 OS CI 抓到黑邊斷言過嚴：本機 libx264 重現邊界亮度達 5；避開邊界後 Linux／Windows 通過，但 macOS 硬體編碼仍未通過原本 <4 的斷言。考慮編碼／解碼的 limited range 黑位與微小雜訊，依協調者裁定改驗黑邊內部的解碼亮度 Y 平均 ≤20、最大 ≤32，另以亮度 >128 的內容欄斷言 x=120..839 與中央 720 px 寬度；正式濾鏡不變。完整 E2E 本機通過。

Codex 指出原片標註匯出尚未反映射；新增測試先重現失敗，再修正。合成 4:3／3:4 原片的雙軌標註影片均解碼核對鼻子圓點位置，並核對傳入即時膝角的姿態與原片座標誤差 <1e-6；無版本記錄與橫直 16:9 的座標逐位元不變，固定 libx264 的橫直 16:9 標註影片整檔也相同。

24 支實片重算依共用 heavy 鎖一次一支，開跑前與每 30 秒檢查 free+inactive ≥8 GB。影片、影格、骨架與逐片結果均不提交或上傳。本機 CI 使用的 Python 測試通過，依賴其他私有場次的 `test_hand.py` 未執行；三 OS CI、最新 head 的 Codex 審查與最終隱私掃描狀態見 [PR #94](https://github.com/Kooooojun/tennis-analyzer/pull/94)。
