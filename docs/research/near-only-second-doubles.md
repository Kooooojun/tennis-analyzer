# #60：第二支雙人調參片，只留近端的拍（調參，負結果）

2026-11-25（台灣時間）。對應 [#60](https://github.com/Kooooojun/tennis-analyzer/issues/60)，接著 [雙人對打只留近端](attrib-near-only.md)（#172）和 [漏掉近端擊球](https://github.com/Kooooojun/tennis-analyzer/pull/173)（#173，寫這份筆記時還沒合併）。基線 `636a4e7`，**沒有改程式**。

## 結論

**#173 試過的改法，加上第二支調參片之後一樣沒有一個能用，不改 `events.py`／`candidates.py`。**

- 第二支片（使用者的雙人對打影片 C）在現行流程上：漏掉近端 3／23 拍，教練的拍收進來 0／18 拍。
- 漏掉的 3 拍**全都是擊球聲太弱**（寬頻聲低於 4 dB），手速都夠、骨架也沒跳。影片 B 的 6 拍漏拍則是聲音 2、髖部跳動 3、手速峰太早 1。兩支片的原因組成**不一樣**。
- 重量 #173 的 4 種改法：每一種都讓至少一支對牆片的準確率下降，或讓練習片 D 少抓真擊球。唯一能在影片 C 救回 1 拍的是把聲音門檻降到 3 dB（`BB=3.0`），但它讓對牆 B 的準確率從 88.0% 掉到 84.6%。

這兩支都是**調參資料**（一個人標、不是保留集）。數字只在調參資料上量過，沒有獨立驗證。

## 資料與手標

- 使用者的雙人對打影片 C：5 分 18 秒、60 fps、1920×1080。和影片 B 同一天、同一個機位（底線後斜角），近端是另一位學員，網對面是同一位教練。這支片的鏡頭固定不動（影片 B 的鏡頭會跟著轉），中間有剪接，也有別人經過鏡頭前。
- prep 用兩人模式跑。和影片 B 一樣，兩個姿態槽被合成**一條軌**（各看到 11549／6749 格，合併後 17942 格），遠端教練幾乎抓不到骨架，所以 `who_hit()` 只有一個人可選。498 個聲音候選，聲音延遲量到 3 格。近端那人的持拍手是從畫面看出來的右手，寫進本機的 `profiles.json`，沒有另外問使用者。
- 手標：從 `sounds.npy` 第 0 號起**連續**看到第 163 號（前 108.3 秒，`# span 0 108.29`）。每個聲音一列：聲音時間的全畫面 1 格、以姿態軌置中的近端放大 4 格（−0.10／−0.03／+0.03／+0.10 秒）、網對面放大 4 格。
- 標成：近端打（N）、教練打（C）、不是擊球（O，含引拍、收拍、走路、剪接後別人經過）、看不清（`?`、`C?`，不計分，評分時當忽略區）。
- 結果：**N 23 拍、C 18 拍，共 41 拍**；O 89 個、不確定 34 個（`C?` 13、`?` 21）。不確定的多半是近端那人走出畫面，或教練兩個相鄰聲音分不出哪一個才是接觸。
- **對流程輸出是盲標**：標完才跑 `candidates.py`、才打開 `events.npy`。但近端放大圖是用姿態軌置中，標註和評分是同一個人。第 0–23 號一開始用較小的網對面縮圖標，放大後重看一次，只把第 15 號從 O 改成 `C?`，計分的 41 拍沒變。
- 範圍內的偵測沒有一個落在 `?`／`C?` 的忽略區裡，所以忽略區沒有藏掉誤收。
- 標註、縮圖、輸出只放在本機的 `testset/results/`，不進 git。

影片 C 的 3 個其他誤收都不是教練的拍：2 個是近端那人在跑位（第 14、104 號），1 個是剪接後另一個人走過鏡頭前（第 108 號）。

## #173 改法的重量（3 支對牆＋練習片 D＋兩支雙人片）

用 #173 的 `events_near_sweep.py`（`eval_hits` ±3 格）。每格是「TP／FN／FP」；準確率指 precision。main 每一行都 `same=True`（和 work 目錄裡的 `events.npy` 完全相同）。

| 版本 | 對牆 A | 對牆 B | 對牆 C | 練習片 D | 雙人 B 近端 | 雙人 C 近端 | 教練被收（B＋C） |
|---|---|---|---|---|---|---|---|
| main | 12／6／25 | 22／3／3；88.0% | 17／0／4；81.0% | 64／0／61 | 18／6／1 | 20／3／3 | 1／36 |
| `RALLY=(1.2, 4.0)` | 12／6／**27** | 不變 | 不變 | **63／1**／65 | 19／5／2 | 20／3／**5** | 1／36 |
| `BB=3.0` | 12／6／**27** | 22／3／**4**；**84.6%** | 不變 | 64／0／**70** | 18／6／2 | **21／2**／3 | 1／36 |
| `JUMP_R=5` | 14／4／26 | 22／3／**6**；**78.6%** | 不變 | 不變 | 19／5／2 | 20／3／**4** | 1／36 |
| 手速窗往前多看 4 格（`SLACK=4`） | 13／5／31 | 不變 | 17／0／**5**；**77.3%** | **61／3**／75 | 19／5／2 | 20／3／3 | 1／36 |

- 對牆 B、C 是逐格完整標註，FP 增加就是真的多收錯誤；對牆 A、練習片 D 的標註只涵蓋舊候選，新偵測一定算 FP，所以 FP 增加還沒核對，但 TP 減少是真的變差（見 #173）。
- 選 `RALLY` 是因為它在對牆 B、C 都不變（#173 裡最有希望）；選 `BB=3.0` 是因為影片 C 的漏拍全是聲音太弱。兩個都過不了：`RALLY` 在練習片 D 少抓一拍有標註的真擊球（60.50 s），同時多出一個 61.17 s 的偵測（沒有核對畫面），在影片 C 救不回任何一拍、多收 2 個；`BB=3.0` 讓對牆 B 多收 1 個確定的錯。
- `BB=3.0` 在影片 C 救回的是第 145 號（反手）。這拍的持拍手腕從鏡頭後方看不到，這裡算的揮拍幅度是 0.00，`candidates.py` 的 arc ≥ 0.7 門檻多半還是會丟掉它（沒有實際重跑 `candidates.py` 確認）。
- 教練的拍在所有版本都只收進 1／36，「誤收教練」不是這兩支片的主要問題。

## 已知限制與後續

- 兩支片都是同一天、同一個機位、同一位教練，一個人標、標註和評分同一個人。教練的拍合計只有 36 拍，誤收率的 95% 上限是 14%。
- 機位不是拍片方法要求的側面 90°；影片 B 的鏡頭還會跟著轉。
- 漏拍的大宗是擊球聲太弱，要從 `hits.py` 或別的證據（例如球的轉向）下手，不是調 `events.py` 的門檻；這裡只記錄，不開新卡。
- 等照拍片方法拍的雙人影片進來，再用保留集量這兩個數字。

## 重現

從 repo 根目錄、用 venv 的 Python（路徑換成自己的）：

```text
python tools/prep.py <session> 2
python tools/candidates.py <session>
python docs/research/near_only_measure.py <work>/<影片> <work>/cands.json <手標>/near_labels.csv
python docs/research/events_near_sweep.py <manifest.txt> [RALLY=(1.2,4.0) | BB=3.0 | JUMP_R=5 | SLACK=4]
```

`events_near_sweep.py` 在 #173 的分支上。`manifest.txt` 每行 `<名稱> <work 目錄> <labels.csv> [player]`，雙人片用近端專用標註並加 `near`。近端專用標註：近端打＝`near,stroke`、教練打＝`coach,stroke`、不確定＝`other,unsure`、不是擊球＝不寫（落在那裡的偵測算 FP），範圍寫在 `# span`。標註和輸出只放本機，不進 git。
